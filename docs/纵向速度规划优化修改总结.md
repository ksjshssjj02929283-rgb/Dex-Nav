# 2026-08-24 至 2026-08-27 速度规划与终点控制修改总结

> 更新时间：2026-08-27
>
> 对比基线：`origin/feature/linfeng.guo/refine_speed_planner`，提交 `015c76c2`
>
> 当前状态说明：本地优化版仍是基线提交之上的未提交工作区，不是一个已经冻结的 Git 版本。正式进行 50 次对比测试前，必须先保存当前源码、参数和二进制哈希，否则后续无法严格复现实验版本。

## 1. 总体结论

周一开始的修改不是一次单点调参，而是沿着以下链路逐步展开：

```text
IMU/odom状态估计
    ↓
速度规划初始v/a裁决
    ↓
S曲线剩余轨迹重规划与跨周期连续性
    ↓
RPP/PID消费轨迹速度和加速度
    ↓
终点0.05m/s蠕动、最终停车和角度校准
    ↓
记录、诊断与实机回归
```

当前保留的总体思路是：

- 计划速度、计划加速度和旧轨迹前缀负责维持S曲线跨周期连续性。
- IMU+odom纵向估计不直接接管规划，只对计划加速度做有限纠偏。
- 终点前5cm的目标是稳定到约0.05m/s，而不是提前规划到0。
- 只有进入动态最终停车距离后，才将最终速度锁存为0。
- 控制器已经低于非零空间目标时，不再重复使用矛盾的负加速度前馈继续压低速度。

当前版本从少量实测看已经改善了“末端降到0再恢复”“终点前反复加减速”等问题，但EKF的独立收益、终点过冲率和任务时间仍需通过后续A/B消融与50次统计验证，不能只靠目前几次实测宣布最终有效。

## 2. 前置工作：odom、IMU与标定

这部分标定工作开始时间早于本周一，但它是周一以后所有实测融合修改的基础。

### 2.1 测量odom和IMU频率

确认：

- `/feedback/odom`约100Hz。
- `/imu/chassis/refined`约100Hz。
- 两者频率足够支持100Hz纵向估计和10Hz速度规划。

优化点：避免继续假设odom只有较低频率，从而使用过长差分窗口造成额外延迟。

缺点/限制：高频不代表低延迟，也不代表加速度可直接通过相邻速度差可靠计算；时间戳、执行延迟和噪声仍需处理。

### 2.2 IMU自动标定脚本

增加自动低速直行、原地转180度、返回的标定流程，输出：

- 原始odom与IMU序列。
- 静止偏置和噪声。
- IMU相对odom的时延。
- 比例、截距、相关性和RMSE。
- IMU安装x偏移及转动补偿所需数据。
- 可直接参考的参数YAML。

期间修复：

- odom回调已收到数据但运动状态判断发生超时的问题。
- 返回距离使用错误方向导致机器人没有真正返回的问题。
- 每次标定输出散落多个文件，改成家目录下单独结果文件夹。

收益：参数不再完全靠猜，能够用10轮标定结果估计比例、偏置和延迟。

限制：标定结果依赖地面、轮胎、机器人启动后的IMU初始姿态和robot_server初始化状态。当前动态bias由估计器静止学习，因此静态标定参数不能永久代替在线bias处理。

## 3. 第一轮：直接使用odom/IMU实测加速度

### 3.1 odom滑窗加速度估计

最初增加了odom滑窗回归，通过一段时间内的速度变化估计加速度，而不是只用相邻两帧差分。

原问题：远端原始版主要沿用上一周期理论加速度。底盘实际执行跟不上时，规划仍可能认为机器人处在理想加减速状态。

收益：能看到真实底盘是否建立了加速度，理论上可以修正规划与执行的偏差。

缺点：

- 滑窗越短，噪声越大。
- 滑窗越长，转折延迟越大。
- 加减速切换时可能在真实已经减速后仍输出正加速度。
- 仅靠odom差分不能区分测量噪声、轮速抖动和真实纵向动力学。

### 3.2 IMU加速度融合

在odom估计基础上接入`/imu/chassis/refined`，使用标定得到的比例、偏置、时延和IMU安装偏移。

收益：IMU能更快感知加速度方向变化，odom能约束长期速度漂移，两者具有互补性。

缺点：

- IMU噪声会直接放大为规划a0波动。
- 转弯时存在向心加速度和安装杆臂影响。
- `/imu/chassis/refined`的向量坐标语义与orientation语义不完全一致，若下游仍按普通机体系消息处理，会重复或错误去重力。

状态：最初的直接融合结构已经被后面的独立纵向状态估计器替代。

## 4. 第二轮：简化EKF及其问题

### 4.1 在Controller内部增加简化EKF

最初在Controller内部加入了状态`[v, a, bias]`形式的简化EKF，试图同时估计速度、加速度和IMU偏置。

原问题：直接odom差分和IMU融合噪声较大，希望用EKF降低波动并处理bias。

实测问题：

- 加速度输出仍然有明显波动。
- 降低加速度过程噪声后，加速度估计变平滑但切换严重滞后。
- 提高过程噪声后，响应变快但噪声重新进入规划。
- 动态过程中bias会吸收一部分真实加速度，导致bias漂移。
- `a`和`bias`都能解释IMU测量误差，模型可观测性和误差分配不够清楚。

结论：这是一次负向或至少不充分的实现。它说明“加一个EKF”本身不能解决问题，错误的状态定义会把真实动力学和偏置学习耦合在一起。

状态：旧简化EKF已经彻底删除，没有继续在其上叠模块。

## 5. 第三轮：PX4思路的独立纵向状态估计器

### 5.1 新建`nav2_longitudinal_state_estimator`包

将状态估计从Controller中拆出，新增独立包：

```text
nav2_longitudinal_state_estimator
```

状态改为：

```text
x = [velocity, imu_bias]
```

主要模型：

```text
v(k+1) = v(k) + (imu_acceleration - bias) × dt
odom_velocity在自己的延迟时间戳上校正velocity
```

原简化EKF中的“加速度随机游走状态”被删除。加速度由去bias后的IMU输入经过独立滤波得到，不再和bias共同作为两个可互相替代的状态。

收益：

- 状态和传感器物理含义更清楚。
- odom校正速度，IMU负责高频传播。
- bias主要在静止阶段学习，运动中冻结，避免真实加速度被bias吸收。
- 估计器职责从Controller中分离，生命周期、参数、测试和诊断更清晰。

代价：

- 新增一个包、节点、消息、启动与依赖关系，部署复杂度上升。
- 估计器有效不等于导航一定有效，仍需消融测试证明它对过冲和跟踪有实际收益。
- IMU和odom本身都来自底盘系统，不是完全独立的真值源。

状态：保留并启用，当前100Hz发布`/navigation/longitudinal_state`。

### 5.2 延迟融合与当前时刻输出预测

参考PX4的思想，将滤波状态保留在一个延迟融合时刻：

- odom按自己的时间戳校正延迟状态。
- 缓存融合时刻之后的IMU样本。
- 输出时重新播放这些IMU样本，预测到当前时刻。

收益：避免所有输出永久停留在最慢传感器的几十毫秒以前。

代价：

- 时间戳错误、乱序或样本过晚时需要拒绝或重置。
- 输出预测只能降低已知延迟，不能消除通信和底盘执行延迟。
- 参数过激仍会把IMU噪声放大到当前时刻。

### 5.3 bias静止学习、运动冻结

增加静止判定：速度、角速度和加速度都足够小时更新bias；运动后停止动态学习。

收益：解决旧EKF中bias在动态阶段漂移、吞掉真实加速度的问题。

代价：

- 静止阈值过严时bias更新不足。
- 阈值过松时轻微运动会污染bias。
- 长时间运动中的温漂不能被立即修正，只能等待下次静止。

### 5.4 IMU坐标语义修正

发现`robot_server`对`/imu/chassis/refined`的加速度向量已经做静态水平对齐，但仍保留原IMU orientation。若下游继续把向量当作原机体系，会发生坐标语义不一致。

按照要求只修改新估计器，不修改robot_server：

- `input_is_level_aligned=true`。
- 用首帧orientation建立与已发布水平向量匹配的参考x轴。
- 后续只计算相对姿态引起的重力x分量。
- 再做静态比例、杆臂和在线bias处理。

收益：避免简单地对已水平旋转过的向量再次按原机体系完整旋转和去重力。

限制：该修正依赖robot_server当前发布语义。如果server未来改成标准机体系消息，估计器参数也必须同步切换。

### 5.5 启动、生命周期与依赖接入

修改bringup启动文件、package依赖和Controller订阅，使独立估计器在普通节点和composition两种启动模式下都被加载，并加入生命周期管理链路。

曾出现的问题：机器人替换文件后ControllerServer无法active，原因是新包、依赖、消息或安装产物未完整同步，而不是导航算法本身失败。

收益：估计器成为明确的系统组件。

代价：同步机器人时不能只复制一个`.cpp`，必须同步新包、依赖、启动、参数和消息接口，并保证编译安装顺序正确。

## 6. 规划初始加速度：从“纯实测”回到“计划为主、实测纠偏”

### 6.1 纯实测加速度作为每周期a0

曾尝试让S曲线每周期直接使用EKF实测加速度作为规划起点。

实测表现：机器人速度经常只能维持在约0.2m/s，难以上升到规划的0.5～0.6m/s。

原因：

- Ruckig每100ms重新规划。
- 一周期内底盘尚未完全执行理论加速度，下一周期又从偏小的实测a重新开始。
- jerk限制使每次都只能慢慢建立加速度。
- 重规划反复把加速过程拉回较早阶段，形成“加速度有，但速度长期上不去”。

提高jerk能够缓解，但会增加冲击，不能根治跨周期计划状态被实测不断重置的问题。

结论：纯实测a0对当前10Hz重规划结构是负向方案，已经取消。

### 6.2 当前方案：计划连续值为主，实测有限纠偏

当前保留：

- 上周期Ruckig计划加速度负责jerk连续性。
- EKF实测加速度只在有限增益和创新范围内修正计划值。
- 向前运动时不会相信底盘尚未建立的过强理论减速度。
- 更大的正加速度会保守地进入停车距离预测。

当前核心参数：

```text
planned_correction.gain = 0.15
planned_correction.innovation_limit = 0.30m/s²
conditioner范围 = [-0.60, +0.70]m/s²
最大负jerk修正速率 = 0.70m/s³
```

收益：兼顾S曲线连续性和真实执行纠偏，解决纯实测导致的长期低速。

代价：

- 增益太小，执行偏差纠正慢。
- 增益太大，会重新引入实测噪声和迟滞。
- 计划值与实测值偏离很大时仍需要独立失效与恢复逻辑。

状态：保留。用户定义的“阶段1”核心就是这一版规划起点语义及其后续保留的空间连续性方案。

### 6.3 纵向运动学参数统一

将S曲线、Controller、RPP和下游约束统一到当前主要纵向能力：

```text
最大加速度：+0.70m/s²
最大减速度：-0.60m/s²
最大jerk：0.70m/s³
控制周期：0.10s
```

原问题：不同模块仍残留0.5/0.4等旧限制，导致规划、控制和执行对“机器人能力”的假设不一致。

收益：加减速更加对称，任务效率提高，测试中角度/线速度部分过冲有所减少。

风险：参数是允许上限，不代表底盘在任何工况都能达到；地面、负载和底盘闭环能力不足时，仍可能出现`terminal_infeasible`或跟不上规划。

## 7. 中间动态障碍与终点制动状态分离

曾出现“只要某周期加速度为负，就可能一直进入禁止重新加速的终端状态”的风险。对中途动态障碍来说，障碍解除后必须允许重新加速，不能污染目标点终端锁存。

修改内容：

- 区分`PATH_OBSTACLE_STOP`和`GOAL_TERMINAL`。
- 障碍停止分支不写入目标点`terminal_brake_latched`。
- 只有目标点终端制动允许锁存。
- 合法障碍停车或碰撞急停期间暂停progress checker；障碍解除时重置进展计时基线。

收益：中途障碍物消失后可以重新规划并恢复巡航，不会被误认为已经进入终点禁止加速段。

代价：

- costmap动态变化会频繁切换障碍分支。
- 障碍分支、Controller避障能力和progress checker三者需要保持一致。
- 如果诊断只看`boundary_should_stop_for_path_obstacle`而不看实际`terminal_branch`，容易误判每周期都在停车。

状态：保留。

## 8. 终点速度方案的多次迭代

### 8.1 终点前30cm限速0.25m/s

曾加入终点前约30cm的0.25m/s上限。

目的：让机器人更早进入可控低速，给底盘和PID预留减速距离。

实测收益：部分测试中过冲减小。

问题：

- 0.25只是包络，不保证Ruckig在该点已经降到0.25。
- 多套距离参数叠加，终端逻辑难以解释。
- 可能过早进入低速区，任务效率下降。
- 仍不能保证最后平滑到0.05。

状态：已删除，不再保留30cm固定限速。

### 8.2 终点前5cm达到0.05m/s

当前目标：机器人在实际终点前约5cm达到0.05m/s，然后低速接近目标。

参数：

```text
end_speed = 0
terminal_speed_cap = 0.05m/s
terminal_creep_distance = 0.05m
terminal_execution_delay = 0.20s
```

收益：

- 不需要像汽车那样提前长距离预停车。
- 给2cm位置精度保留低速校准能力。
- 终点附近速度不再保持0.2～0.3m/s。

问题：仅把末点设置为0、末端区域设置为0.05仍可能使完整S曲线为了满足末点0，提前降到0，再从空间包络恢复到0.05。

### 8.3 两阶段空间终端

最终把终端拆成两个空间阶段：

1. 高速/巡航阶段提前反推减速，在固定5cm边界达到0.05。
2. 进入0.05→0所需动态停车距离后，才锁存最终停车，目标改为0。

收益：避免在距离终点仍较远时就规划到0再重新起步，减少长距离蠕动。

代价：

- 当前加速度状态、执行延迟和剩余距离不匹配时仍可能不可行。
- 最终停车触发过早会重现提前到0；触发过晚会增加过冲。
- 空间投影不前进时，速度目标也不会沿终端曲线继续推进。

状态：保留。

### 8.4 删除冗余终端距离

清理了多套相互叠加的终端距离：

- 删除额外`terminal_safety_margin`。
- 删除旧`latched_terminal_reserve`等重复安全距离。
- 障碍分支不再叠加终点执行余量。
- 终点高速命令提前量只保留`v × terminal_execution_delay`及必要加速度项。
- 配置中的旧approach入口速度/距离限制设为关闭或移除其影响。

收益：5cm重新成为明确的物理边界，不会因为多个margin叠加而提前几十厘米蠕动。

风险：删掉冗余余量后更依赖`terminal_execution_delay`和底盘真实制动能力准确；参数低估会导致到边界时速度仍偏高。

### 8.5 稳定0.05附近的加速度噪声归零

当尚未进入最终停车、速度已经接近0.05且加速度很小时，将厘米级加速度噪声视为0，避免S曲线解释成“必须先继续减速再恢复”。

收益：降低稳定蠕动阶段的速度波动。

代价：阈值过宽会掩盖真实的小减速度；因此只在0.05附近、最终停车未锁存时生效。

状态：保留。

## 9. 到点PID、固定目标和位置滞回

### 9.1 末端固定目标

PID进入approach后固定瞄准最终目标，不再在末端轨迹的多个最近点之间跳动。

原问题：机器人位置和轨迹点有厘米级变化时，最近点索引可能变化，引起速度和角度目标跳变。

收益：位置误差和目标角度语义稳定，更适合厘米级到点。

代价：固定最终目标后，若朝向控制过强，可能在还未完成位置收敛时抢先转角度。

状态：保留，当前`final_target_lock_distance=0.3m`。

### 9.2 2cm进入、4cm退出的位置滞回

进入最终位置保持仍使用2cm精度；一旦进入后，只有误差超过4cm才退出位置保持。

收益：定位在2cm边界附近抖动时，不会每周期在平移和旋转状态之间切换。

必须强调：4cm不是允许的到点精度，只是已经进入状态后的退出阈值。

代价：进入后如果定位缓慢漂到2～4cm区间，控制器会继续保持当前状态而不是立即重新平移。

状态：保留，`position_hold_hysteresis=0.02m`。

### 9.3 清除位置/速度PID积分并锁定零线速度

进入最终角度旋转阶段时：

- 清除位置PID和速度PID积分。
- 线速度固定为0。
- 等真实线速度停稳后再开始最终旋转。

收益：防止旧积分或0.05末速在原地旋转时重新推动机器人。

代价：状态切换条件错误时，会表现为过早停车或无法继续完成位置误差。

状态：保留。

### 9.4 最终角速度改为Ruckig角S曲线

最终角度不再完全依赖纯P角速度，增加角速度、角加速度和角jerk限制：

```text
max_w = 0.50rad/s
max_angular_accel = 0.80rad/s²
max_angular_jerk = 1.50rad/s³
```

收益：理论上避免角速度一步跳变，接近目标角度时平滑制动。

问题与风险：

- 早期版本出现未接近目标角度就左右摆动，说明不只是“角速度过冲”，还涉及目标方向、状态切换和路径/最终角度语义。
- 位置重试、角度重试和最终旋转之间仍可能相互切换。
- 当前纵向优化测试不能证明角度问题已经完全解决，应单独统计角度反向次数和角过冲。

状态：保留但仍属需要专项验证的部分。

## 10. 轨迹消费与跨周期连续性

### 10.1 轨迹速度与加速度消费语义统一

RPP和PID改为从`RobotTrajectory`消费速度、加速度和相对时间，而不是只使用普通路径点或单一最大速度。

同时修正“峰值速度点配上离开该点的减速度”造成的`v/a`语义矛盾：空间fallback选择速度点时，前馈加速度尽量使用到达该速度点的段加速度。

收益：控制器消费的速度和加速度来自同一条S曲线，减少“目标仍要求加速/保持，但前馈已经最大减速”的冲突。

代价：轨迹点时间、空间投影和前瞻必须统一；任一消费者使用不同语义都可能重新产生冲突。

状态：保留。

### 10.2 初始运动状态裁决器

扩展`InitialMotionArbiter`，检查：

- 时间是否过期。
- frame、目标点和路径分支是否一致。
- 空间投影误差。
- 实测速度与旧轨迹采样速度偏差。

当前规则：

- 偏差小于`replan_dev=0.10m/s`：继承计划速度和加速度。
- 超出门限：速度重锚到实测，但尽量保留计划加速度连续性。
- 连续5周期超限：完整reseed，计划已经系统性脱离现实。

收益：避免每周期无条件使用odom速度破坏S曲线，同时保留真实严重偏差时的兜底。

代价：

- 门限过大，计划可能已经明显脱离实测仍继续拼接。
- 门限过小，正常噪声会频繁清除连续性，引起速度抖动。
- 全局单一门限不能完美覆盖巡航、终端和后退恢复三种工况。

状态：保留。

### 10.3 完整空间轨迹前缀拼接

不再只继承一个`v/a`，而是保留上一周期约0.2秒的未来轨迹前缀，包括：

```text
pose + velocity + acceleration + relative_time
```

新周期验证前缀仍贴合最新局部路径后，从前缀尾点规划新的Ruckig后缀，再拼接为完整轨迹。

收益：

- 避免每周期从一个孤立状态重新生成完全不同曲线。
- 正常路径中速度、加速度和jerk跨周期更连续。
- 当前多次测试中约55%～63%的周期能够成功拼接。

代价和已知边界：

- 当前拼接以空间投影为主。机器人没有空间进度时，会重复消费同一段速度。
- prepare固定后退2秒后，机器人位于新路径起点后方，路径投影钉在起点，控制目标会约0.032m/s保持数秒，直到重新接近路径起点。
- 这是效率问题，不是EKF加速度错误；目前决定暂不修改。

状态：保留。

### 10.4 Apollo式累计时间推进尝试

曾尝试加入更完整的相对时间累计：下一周期不再重复读取旧轨迹相同的`t≈0.1`，而是按真实经过时间继续推进旧轨迹。

目的：解决位置进度小的时候重复消费同一段减速度。

实测问题：

- 靠近终点的目标更抖。
- 容易从较高速度直接降到0，再从0恢复。
- 当底盘没有完成相应空间进度时，纯时间继续推进会使计划提前走到终点状态，机器人可能停在目标之前。
- 当时只是把时间推进叠加在当前重规划结构上，没有完整实现Apollo的绝对时间轨迹、误差门控和轨迹重建体系。

结论：该尝试为负向优化，已经原样回退，不以`bool=false`形式残留。

当前用户定义：回退后的空间拼接＋计划/实测有限融合版本称为“阶段1”。

## 11. 终端停滞恢复

增加一次性`terminal_stall_recovery`：

当同时满足以下条件约0.5秒：

- 处于APPROACH。
- 是目标终端而不是障碍停车。
- 终端制动已锁存。
- 规划仍消费非零速度且给负加速度。
- odom已经基本静止。
- 路径进度基本不变。
- 距离终点仍大于最小恢复距离。

则只清除旧轨迹拼接前缀，保留终端锁存，下一周期从真实静止状态重新规划。

收益：旧轨迹与机器人现实彻底脱离时，不会永久卡死。

代价：

- 它是兜底而不是正常控制。
- 触发后紫色“控制器消费目标”会从旧计划值突然降到基于静止状态的新值，再重新升到0.05。
- 如果频繁触发，说明上游控制或拼接仍有根因，不应把恢复次数增加当成优化。

状态：保留，同一目标最多触发一次。最新`20260827_103508_change_after`中触发次数为0。

## 12. PID负加速度前馈一致性保护

### 12.1 初版：目标不超过0.06时禁止继续制动

发现末端存在以下闭环：

```text
空间目标仍约0.073m/s
规划加速度仍约-0.11m/s²
控制cmd和odom已经接近0
机器人不前进
空间目标继续停在0.073
下一周期又执行同一负前馈
```

初版只在非零目标不超过0.06m/s时，若cmd和odom均落后目标，则把最终负加速度命令钳到0。

收益：保护0.05蠕动区，目标0仍保留完整停车权。

缺点：实际异常目标约0.073，高于0.06，保护没有触发；而且简单钳成0只能冻结已经过低的cmd，不能利用正速度误差恢复空间进度。

### 12.2 当前版：覆盖到0.10并保留正反馈

最新修改：

- 保护目标范围扩到0.10m/s。
- cmd和odom均明显低于非零目标，且规划前馈仍为负时，只撤销矛盾的负前馈。
- 保留PID正向速度反馈，使机器人重新获得空间进度。
- 目标0、cmd仍高于目标和0.10m/s以上的正常制动完全不受影响。

收益：针对`20260826_190902`中目标0.0805、前馈-0.148、cmd/odom已低于目标的实测场景，避免控制器主动压到0。

最新结果：`20260827_103508_change_after`大致符合预期，`terminal_stall_recovery=0`，终端前未记录目标二次加速。

风险：

- 这是PID对空间轨迹前馈的语义修正，不改变S曲线本身。
- 保护范围过大可能削弱需要提前制动的能力，因此当前只覆盖0.10m/s以内。
- 仍需50次统计确认过冲率和任务时间没有恶化。

状态：保留，为当前最新修改。

## 13. prepare后退后的慢速回归现象

当前prepare配置：

```text
检测到前方/侧方障碍后
固定-0.10m/s后退2秒
只检查后方是否安全
不会因为前方障碍提前清除而提前结束
```

后退约0.2m后，机器人可能位于新路径起点后方。局部规划器的投影被钉在路径起点，RPP为了避免零速自锁会消费S曲线向前一个控制周期的首个非零目标，约0.0316m/s，而不是0。

因此出现：

```text
约0.032m/s慢速返回路径起点
接近原路径起点后空间进度恢复
速度随后正常升高
```

这不是本周EKF或最新PID保护造成的，慢速期间规划a0仍为正。它是旧prepare固定后退与当前空间拼接组合后的边缘效率问题。

当前决定：暂不修改。它不破坏安全和导航正确性，但会增加后退后的任务时间。后续若优化，应增加专门的post-backup recovery或更合理的障碍清除提前退出，不能靠提高jerk解决。

## 18. 尚未证明或仍需解决的问题

1. **EKF是否是有效导航优化**：架构更合理，但必须用当前完整版本的“EKF参与”和“EKF只旁路记录”做同代码消融，比较未来速度预测、过冲率、任务时间和jerk。
2. **终点过冲统计**：目前主要是少量实测，不能代替50次过冲率和置信区间。
3. **最终角度摆动**：纵向改善不能证明角度控制已经解决，应单独统计角度目标跨越、反向次数和角速度过冲。
4. **空间拼接与严重执行落后**：`replan_dev=0.10`可能在部分终端工况中过于宽松；不能在没有A/B数据时直接全局收紧。
5. **prepare后退恢复效率**：安全正确但可能以0.032m/s慢速返回路径起点数秒。
6. **版本可复现性**：当前大量改动未形成阶段提交。过去的`change_after`数据没有保存代码和参数哈希，只能作为探索证据，不能严格证明每一步因果。
7. **曲率约束当前关闭**：弯道主要依赖RPP调速，S曲线层的物理横向加速度约束尚未单独上机验证。

## 19. 对本周修改的阶段性评价

### 明确负向并已撤销

- 旧`[v,a,bias]`简化EKF。
- 每周期纯实测加速度作为S曲线a0。
- 多套30cm/安全margin叠加的终端距离。
- 仅靠真实时间累计推进旧轨迹的简化Apollo尝试。

### 结构上合理但仍需统计证明

- 独立PX4思路纵向状态估计器。
- 计划加速度＋实测有限纠偏。
- 完整空间轨迹前缀拼接。
- 5cm/0.05m/s两阶段终端。
- 最终角Ruckig和位置滞回。

### 已有较直接实测证据支持

- 纯实测a0会导致速度长期上不去，恢复计划连续值后速度恢复。
- 旧终端前缀可能把机器人压停，stall恢复能解除但会造成目标跳变。
- PID目标0.06保护范围不足以覆盖0.073异常；扩展到0.10并保留正反馈后，最新测试没有再触发terminal stall恢复。
- 后退后0.032慢速不是EKF负加速度，而是空间投影钉在路径起点。

最终是否构成“整体正优化”，应以接下来冻结版本后的A/P/E随机分块50次测试为准。
