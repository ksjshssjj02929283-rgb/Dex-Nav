# 速度规划、EKF与历次优化对比测试方案

> 制定时间：2026-08-27
>
> 基线分支：`origin/feature/linfeng.guo/refine_speed_planner`
>
> 基线提交：`015c76c2`

## 1. 测试目标

本测试同时回答三个问题：

1. 当前最终优化版相对远端最初版本，跟踪精度、终点过冲率、任务时间和平滑性是否真正改善。
2. EKF是否对导航性能有独立贡献，而不是增加复杂度但没有实际收益。
3. 从周一到现在的每个主要修改是正向、反向、中性还是只在特定场景有效。

总体方法采用：

```text
版本冻结
  + 随机分块运行
  + 统一路线和环境
  + 自动数据采集
  + 预先定义指标
  + 置信区间和消融分析
```

不能先连续运行50次旧版、再连续运行50次新版，否则电池、温度、定位漂移、现场人员和时间变化会被错误归因于版本差异。

---

## 2. 核心实验版本

建议先冻结三个核心版本：

| 组别 | 版本 | 作用 |
|---|---|---|
| A | 远端原始版本`015c76c2` | 理论加速度、无EKF、无当前旧轨迹前缀优化 |
| P | 当前全部优化，但EKF只运行和记录，不参与规划 | EKF消融组 |
| E | 当前完整优化版，EKF参与有限纠偏 | 最终优化组 |

比较关系：

- A与E：回答“最终优化版相对最初版本是否整体变好”。
- P与E：回答“EKF在当前完整架构中是否有独立收益”。
- A、P、E各运行50次完整`L1→L2→L3→L1`任务。
- 三个版本共150次正式任务，预热运行不计入样本。

若要进一步证明EKF优于简单实测反馈，可增加O组：

| 组别 | 版本 | 作用 |
|---|---|---|
| O | 当前架构，使用普通odom滑窗差分加速度，不使用IMU+EKF | 简单实测反馈对照 |

O组可先运行20次筛选，结果接近时再扩展到50次。

---

## 3. 版本冻结与可复现要求

### 3.1 冻结源码和参数

- A固定为远端提交`015c76c2`。
- 当前E版本保存为不可变化的源码快照。
- P必须与E使用完全相同的代码、运动学参数、Controller和终点逻辑，只关闭“EKF结果进入规划a0”；估计器仍继续运行和记录。
- O若实施，也必须使用同一套当前代码，只切换加速度输入模式。

### 3.2 每次记录必须保存的版本信息

正式测试前需要扩展记录脚本，每次运行自动保存：

```text
版本A/P/E/O
Git提交号
未提交diff的SHA256
参数文件SHA256
nav2_controller动态库SHA256
nav2_speed_planner动态库SHA256
nav2_pid_controller动态库SHA256
nav2_longitudinal_state_estimator动态库SHA256
Ruckig版本
当前controller、speed planner和local planner
实验块编号
块内运行序号
测试开始和结束时间
```

如果没有这些信息，测试中途同步错文件或参数后很难发现，所得结果不能作为严格版本比较。

---

## 4. 测试顺序与随机分块

### 4.1 禁止的运行顺序

不要这样运行：

```text
A连续50次 → P连续50次 → E连续50次
```

### 4.2 推荐运行顺序

每个版本连续运行10次作为一个实验块，采用平衡顺序：

```text
A → P → E
P → E → A
E → A → P
A → E → P
P → A → E
```

最终每个版本获得5个实验块，即50次正式运行。

每次切换版本后：

1. 启动并等待导航节点、costmap、odom、IMU和纵向估计器稳定。
2. 运行一次预热任务，不计入正式数据。
3. 确认机器人距离L1不超过2cm，朝向满足路网起点要求。
4. 确认现场没有动态障碍进入主路线。
5. 再开始本块10次正式任务。

---

## 5. 环境与运行条件控制

所有版本保持一致：

- 同一机器人、地图和路网。
- 同一路线`L1→L2→L3→L1`。
- 同一Theta*全局规划器。
- 同一RPP跟踪Controller和PID approach Controller。
- 同一Ruckig版本。
- 同一最大速度、加速度、减速度和jerk口径。
- 同一定位、odom、IMU和底盘固件。
- 尽量保持相同电池电量区间和地面条件。
- 正式主性能测试期间禁止人员或动态障碍进入路线。

发生以下情况时，该次结果不能直接删除：

- 人员经过。
- 动态障碍触发停车或prepare后退。
- 导航被外部抢占。
- 传感器、TF、节点生命周期或记录脚本异常。

处理方式：

1. 将结果标记为“环境干扰/系统异常”。
2. 不进入纯净性能均值。
3. 单独进入鲁棒性统计。
4. 额外补跑一次，保证每个版本仍有50次有效样本。

导航自身失败、过冲、超时或Controller异常属于算法结果，不能作为环境异常删除。

---

## 6. 跟踪精度指标

### 6.1 速度跟踪

统计：

- 控制器消费目标与odom速度RMSE。
- 控制输出与odom速度RMSE。
- 速度平滑器输出与odom速度RMSE。
- 最大瞬时速度误差。
- P95速度误差。
- 通过互相关估计目标到odom的速度跟踪延迟。
- 加速段、匀速段和减速段分别统计误差。

### 6.2 路径跟踪

记录脚本需要增加准确目标坐标以及全局/局部路径数据，计算：

- 横向误差RMSE。
- 横向误差最大值。
- 横向误差P95。
- L1→L2、L2→L3、L3→L1分别统计。
- 实际行驶距离与理论路径长度之差。

路径横向误差必须相对路径几何计算，不能只看odom轨迹形状。

---

## 7. 终点过冲与到点质量

### 7.1 位置过冲定义

每个L1、L2、L3分别统计。

位置过冲使用终点前最后一段路径的进入切向计算：机器人越过终点切向平面后的最大有符号距离为纵向过冲。

不能直接用目标最终朝向计算位置过冲，因为L2等节点的目标朝向可能与进入路径方向不同。

统计：

- 最大纵向过冲距离。
- 超过2cm的有效过冲率。
- 超过5cm的严重过冲率。
- 最终纵向误差。
- 最终横向误差。
- 进入终点30cm范围到任务成功的时间。
- 进入终点5cm范围到任务成功的时间。
- 终点前是否提前停车。
- 是否出现`0→0.05m/s`重新起步。
- 终端速度重新加速次数。
- `terminal_stall_recovery`触发次数。
- 最终5cm内低速蠕动距离和持续时间。

### 7.2 最终角度

角度问题单独统计：

- 最大角度过冲。
- 最终角度误差。
- 角速度方向切换次数。
- 最终校准阶段左右摆动次数。
- 进入最终旋转到完成的时间。
- 未接近目标角度时发生反向旋转的次数。

位置过冲和角度摆动不能合并成同一个“到点过冲率”。

---

## 8. 任务效率指标

统计：

- 完整`L1→L2→L3→L1`任务时间。
- L1→L2耗时。
- L2→L3耗时。
- L3→L1耗时。
- 实际行驶距离。
- 低于0.05m/s但尚未到点的持续时间。
- 原地旋转持续时间。
- 提前停车等待时间。
- prepare后退时间及后退恢复时间。
- 导航成功率。
- 任务超时率。
- Controller失败次数。
- 规划失败与轨迹不可行次数。

失败任务不能只从平均任务时间中删除，应单独报告失败率；必要时将超时上限作为删失时间进行统计，避免只统计成功样本造成幸存者偏差。

---

## 9. 平滑性与控制质量指标

分别对控制器消费目标、控制输出、平滑器输出和odom计算：

- 加速度RMS。
- 加速度最大值和P95。
- jerk RMS。
- jerk最大值和P95。
- 加速度符号切换次数。
- 速度局部峰谷数量。
- 非终点区域重新加速次数。
- 目标速度与控制输出突变次数。
- 角速度峰值。
- 角jerk。
- 角速度正负切换次数。

最大jerk容易被单个噪声点支配，因此必须同时报告RMS和P95。

---

## 10. 规划、拼接与状态估计器指标

统计：

- 计划加速度与EKF加速度RMSE。
- 最终送入速度规划的a0与EKF加速度RMSE。
- 计划速度与实测速度偏差。
- 轨迹拼接成功比例。
- `prefix_unavailable`次数。
- `suffix_infeasible`次数。
- `terminal_infeasible`次数。
- EKF有效数据比例。
- bias最终值、均值和波动。
- odom创新拒绝次数。
- 速度重锚次数。
- 延迟IMU样本拒绝次数。
- EKF预测速度与odom速度偏差。
- 每路段各加速/减速切换的估计延迟。

---

## 11. 统计分析方法

每个版本不能只输出50次平均值，还需要输出：

```text
平均值
标准差
中位数
P95
最小值/最大值
95%置信区间
```

对成功率和过冲率输出：

- 发生次数/总次数。
- 百分比。
- Wilson 95%置信区间。

结果必须：

- 分别统计L1、L2、L3。
- 再统计全任务综合结果。
- 一个完整任务作为一个独立样本。
- 不把同一次任务的三个终点视为三个完全独立实验。
- 使用实验块校正测试时间、电池和现场缓慢变化。

建议提前确定工程判定标准：

- 导航成功率不能降低超过2个百分点。
- 平均任务时间不能增加超过5%。
- 有效过冲率或最大过冲至少改善15%，才认为有明显工程意义。
- 速度跟踪RMSE至少改善10%。
- jerk、角度摆动和提前停车次数不能明显增加。

如果平均值改善但95%置信区间跨过0，应判定为“证据不足”或“效果中性”，不能直接宣布优化有效。

## 12. EKF有效性验证

### 12.1 为什么不能只比较A和E

A与E之间同时存在：

- EKF。
- 计划加速度有限纠偏。
- 空间轨迹前缀拼接。
- 两阶段终端。
- PID负前馈一致性保护。
- 固定目标和位置滞回。

因此A与E整体变好不能证明收益来自EKF。

### 12.2 P与E消融

必须比较：

```text
P：当前所有代码相同，EKF正常运行和记录，但规划a0只使用计划连续值
E：当前所有代码相同，EKF对计划加速度做当前有限纠偏
```

除“是否消费EKF输出”以外，其他代码、参数和测试条件必须完全一致。

### 12.3 未来速度预测验证

在每个时刻`t`计算：

```text
计划预测：
v_plan(t+h) = v_odom(t) + a_plan(t) × h

EKF预测：
v_ekf(t+h) = v_odom(t) + a_ekf(t) × h
```

与未来真实odom速度`v_odom(t+h)`比较，使用：

```text
h = 50ms
h = 100ms
h = 200ms
```

统计：

- 未来速度预测RMSE和MAE。
- 加速/减速方向判断正确率。
- 加速转减速检测延迟。
- 减速转加速检测延迟。
- 静止加速度均值和标准差。
- bias静止稳定性和动态漂移。
- 异常样本和拒绝样本比例。

未来odom没有参与当前时刻估计，因此可以作为时序验证目标。

### 12.4 EKF导航收益判定

EKF只有同时满足以下条件，才可判定为“有效导航优化”：

1. 未来速度预测比计划加速度更准确。
2. 终点过冲、跟踪RMSE或异常停车指标稳定改善。
3. jerk和速度波动没有明显增加。
4. 任务时间和导航成功率没有恶化。

如果EKF预测更准确，但P与E的导航性能无显著差异，应表述为：

> EKF状态估计有效，但尚未证明它对导航有实际收益。

若加入O组，则进一步比较：

```text
P：纯计划连续值
O：普通odom差分反馈
E：IMU+odom EKF
```

只有E比P预测更准确，同时比O噪声更低、jerk更小、导航表现更稳定，才能更有力证明EKF不是多余复杂度。

## 13. 周一至今历次优化验证

### 13.1 建立里程碑

建议按可独立测试的功能组建立版本：

| 阶段 | 内容 |
|---|---|
| M0 | 远端原始理论加速度版 |
| M1 | odom滑窗加速度 |
| M2 | IMU直接融合 |
| M3 | 旧`[v,a,bias]`简化EKF |
| M4 | 独立PX4思路纵向状态估计器 |
| M5 | 计划加速度＋实测有限纠偏，即阶段1 |
| M6 | 终点5cm/0.05m/s及动态最终停车 |
| M7 | 固定目标、位置滞回、最终角Ruckig |
| M8 | 完整空间轨迹前缀拼接 |
| M9 | Apollo累计时间推进尝试版 |
| M10 | 回退后的阶段1空间拼接版 |
| M11 | terminal stall恢复 |
| M12 | PID负前馈保护0.06版 |
| M13 | 当前0.10范围并保留正反馈版 |

无法准确复原的版本必须标记“不可严格复现”，不能凭记忆拼出近似版本后当作原版本。

### 13.2 顺序增量测试

依次比较：

```text
M0 vs M1
M1 vs M2
M2 vs M3
……
M12 vs M13
```

回答：该项修改在当时架构上是正向还是反向。

### 13.3 当前版本消融测试

从当前M13分别删除一个功能：

```text
M13 - EKF
M13 - 空间轨迹拼接
M13 - 两阶段终端
M13 - terminal stall恢复
M13 - PID负前馈保护
M13 - 固定目标和位置滞回
```

回答：该功能在当前完整架构中是否仍然有价值。

顺序增量和最终消融都需要做，因为一项修改可能在早期架构中是负优化，但在当前架构中与其他功能组合后成为正优化。

### 13.4 每个阶段运行次数

- 每阶段先运行10～15次筛选。
- 明显正向或反向的先分类。
- 结果接近、涉及安全或终点性能的扩展到30次。
- 准备正式保留或删除的重要阶段扩展到50次。
- M0、P、E必须各50次。

### 13.5 最终分类

- 正向优化：主要指标改善，安全和时间不恶化。
- 反向优化：过冲、振荡、失败率或任务时间明显恶化。
- 中性：置信区间内没有可区分差异。
- 场景相关：正常路径略差，但在障碍、执行滞后或终点场景明显改善。
- 无法判断：版本无法准确复原或有效样本不足。

## 14. 推荐实施顺序

1. 冻结A、P、E三个核心版本。
2. 完善记录脚本的版本哈希、精确目标位姿、路径误差和EKF预测指标。
3. A、P、E各试跑3次，只验证采集完整性，不计入正式统计。
4. 按随机版本块完成A、P、E各50次。
5. 输出A与E的整体性能比较。
6. 输出P与E的EKF消融结论。
7. 视需要增加O组odom差分测试。
8. 重建M0～M13，每阶段先运行10～15次筛选。
9. 对有争议或准备正式保留的修改扩展到30～50次。

---

## 15. 正式实验前的通过条件

只有满足以下条件后才开始150次正式运行：

- A、P、E均可重复部署并能通过版本哈希确认。
- 记录脚本能够自动结束并完整保存JSON、CSV和PNG。
- 每次结果包含版本、参数和动态库哈希。
- 能计算目标点切向位置过冲，而不只是速度曲线。
- 能区分位置过冲、角度过冲、障碍停车和prepare后退。
- EKF的计划、融合和旁路数据在P、E两组中都能够完整记录。
- 3次试跑的所有关键字段无NaN、时间戳错位或数据缺失。

满足这些条件后，正式统计结果才具备可重复、可解释和可审计性。
