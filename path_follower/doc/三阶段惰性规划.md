# 三阶段惰性速度规划（方案记录，未实施）

> 改动量分档、潜在问题清单，以及建议的落地顺序。
>
> 记录日期：2026-08-26　　讨论背景见文末"起因"。

## 1. 方案描述

当前 `buildAndLoadRoute`（`src/path_follower.cpp:805`）在**收到路径的那一刻**就把三阶段的
速度剖面全部规划完：

```
受理路径
  ├─ pr.position      = planPosition(raw)                              // 阶段二
  ├─ pr.heading_align = planHeading(start_theta, path_start_heading)   // 阶段一
  └─ pr.heading_final = planHeading(path_end_heading, goal_theta)      // 阶段三
```

问题在于阶段二、阶段三的规划起点用的都是**受理时刻的快照**，而这两个阶段真正开始执行时
已经过去了几秒（阶段一原地旋转），定位早就漂了。

**惰性规划**把每一段的规划推迟到该段真实起点已知的时刻：

```
受理路径      -> 只算几何 + 规划阶段一
阶段一结束    -> 用当前定位重新找最近 index、截断、规划阶段二
阶段二结束    -> 用当前真实车体朝向重新离散、规划阶段三
```

---

## 2. 它能治什么、治不了什么

### 2.1 阶段二：只治"超前"，治不了"落后"

关键限制：**截断只能删掉车后面的点，不能凭空补出车后面的点。**

`buildAndLoadRoute:866` 受理时那次截断已经把车之前的点全 `erase` 掉了
（`raw.erase(begin, begin + truncate_from)`），所以阶段一结束时手上没有余量可退。

| 阶段一结束时的定位偏差 | 重新找最近点的结果 | 效果 |
|---|---|---|
| **超前 2cm** | 最近 index 前移 2 格，截掉 → 剖面原点落在车身上 | **治好**：从 `min_v` 正常起爬，不再瞬间平移查表，起步过冲消失 |
| **落后 2cm** | 最近点仍是 index 0，截断量 = 0 | **无变化**：剖面原点还在车前方 2cm，`velProjection` 的 `K<0` 照样被 `src/path_follower.cpp:1868` 夹成 0，`ref_v ≡ points[0].linear_v = 0.01`，走完 2cm 仍需 **2.0 s** |

> 直觉上会觉得"重新找 index 就能往回退 2 格"，但那要求受理时的截断留了余量，现状没有。

**要治落后必须额外做"反向延拓"**：沿轨迹起点切向、按 `trajectory_resolution` 向后补几个点，
让剖面原点真正落到车身上。

注意**不要**直接把当前位姿插到轨迹最前面：当前位姿相对 `points[0]` 除了纵向落后还有横向偏差，
`computeCurvature` 的三点圆法会在这个折角上算出**虚假大曲率**，随后
`applyCurvatureDeceleration` 会把起步速度压得比现在**更低**。沿切向做纯纵向延拓则没有这个问题。

反向延拓只能在阶段一结束时做（受理时不知道旋转期间会漂多少），所以它和惰性化天然配套，
但它是**额外的一块工作**，不是惰性化白送的。

### 2.2 阶段三：主收益所在，修的是一个已有补丁记录的真 bug

`pr.heading_final` 现在是受理时用 `path_end_heading`（轨迹终点切向）当起点规划的，
**不是阶段二结束时的真实车体朝向**。

这件事代码里已经承认并打了补丁 —— `src/path_follower.cpp:2985-2995`：

```cpp
// 前馈耗尽兜底：hed 是规划期离线生成的（起点用规划的 path_end_heading / hold_direction，
// 而不是本阶段真实进入时的车体朝向），前馈转角与实际残差天然对不齐 ...
// 此时按 goal_err 符号补一个最小角速度，把最后这点残差磨掉。
ref_heading_omega = std::copysign(planner_params_.min_angular_velocity, goal_err);
```

`min_angular_velocity: 0.015` rad/s 磨掉 0.05 rad（≈2.9°）的残差需要 **3.3 秒**。

这正是阶段二那个 2 秒延迟的**角度孪生兄弟**：都是"拿规划边界的种子值当参考速度，去爬一段
真实存在的残差"，而且比线速度那个更慢。

惰性化阶段三后，离散区间和梯形前馈都按**真实转角**生成，上面那段补丁可以退回去当纯兜底，
而不是像现在这样成为常态路径。

## 3. 改动量

有一个能大幅减负的观察：**`planPosition` 里几何和速度是可分的，需要推迟的只有速度那一半。**

几何（`computeArcLengthAndHeading` / `computeCurvature`）必须在受理时算：

- 阶段一的旋转目标 `path_start_heading` 取自 `pr.position.points.front().heading_angle`；
- 阶段一里的 `checkTrackDeviation(pose, route.position, 0)` 也要 position 存在。

真正要推迟的只是 `fillPositionVelocityProfile`。而且 `applyCurvatureDeceleration` /
`applyAccelerationEnvelope` **本来就带 `from_index` 参数**，管路已经修好一半。

| 子项 | 量级 | 说明 |
|---|---|---|
| 阶段三惰性化 | **小**（~50 行） | 单一规划入口，diff / omni 两个调用点；不涉及截断，不涉及 index 基准 |
| 反向延拓 | **小** | 阶段二规划入口前按 `trajectory_resolution` 重采样补几个点 |
| 阶段二惰性化 | **中** | `buildAndLoadRoute` 拆分；`PlannedRoute` 变成分步有效；`fillPositionVelocityProfile` 加 `from_index`；4 个阶段转换点；两次截断的 index 基准统一 |

阶段转换点（需要挂规划入口的地方）：

- `diffPhaseAlignToPath` 结束 → 阶段二（`src/path_follower.cpp:2519` 附近）
- `diffPhaseFollowTrack` 结束 → 阶段三（`src/path_follower.cpp:2655` 附近）
- `omniTransPhaseAlignHold` 结束 → 阶段二（`src/path_follower.cpp:2519` 附近）
- `omniTransPhaseFollowTrack` 结束 → 阶段三（`src/path_follower.cpp:2771` 附近）

## 4. 潜在问题清单

1. **落后方向治不了**（见 §2.1），需要单独配一块反向延拓。

2. **失败时机后移 —— 最实质的行为回归。**
   现在规划不出来（点太少、Ruckig 不收敛）在受理时就能拒掉并报 `FAILED`；惰性化后变成
   "车已经原地转完了才告诉你不行"。**上层动作 / 状态机能否接受这个语义变化，必须先确认。**

3. **规划发生在控制环内，且持着锁。**
   阶段转换在 `diffPhaseAlignToPath` 等函数里，而 `update()` 在 `src/path_follower.cpp:2206`
   持着 `route_mutex_`。规划会拉长一个控制周期，还带一堆 vector 分配。30Hz 有 33ms 预算，
   `planPosition` 估计在 ms 量级够用 —— **但这个必须实测，尤其是长路径，不要拍脑袋。**

4. **绝对不能碰 VelocityStepModel 的状态。**
   阶段一期间可能来了障碍，`vel_track_mode_` 正处于 `kStop` / `kSlowdown`。替换剖面时顺手调
   `resetVelocityTrack()` 会让车带着未复位的速度记忆开走 —— `src/path_follower.cpp:2186`
   已经有一条一模一样的警告。**替换的只是参考曲线，`last_track_linear_v_` / `vel_track_mode_`
   必须原样保留。**

5. **`route_` 变成"部分有效"**，所有消费者要能容忍"速度还没填"。
   用"几何早算、速度晚填"的切法基本能消掉这一条。

6. **两次截断的基准要统一**：受理时截一次、阶段二再截一次，`current_s` 的原点、
   `nearest_index_` / `last_index_` 的基准都要重新定义清楚。

7. **三种 mode × 倒车**（`kDiff` / `kOmniTranslation` / `kOmniTransRotation`，
   叠加 `enable_reverse`）要一个个过，四个转换点都要覆盖。

8. **诊断可读性下降**：现在一条 `tracking started: N points, total_s=...` 能看到整段规划结果，
   惰性化后拆成三次打印，回放复盘需要拼。

## 5. 澄清：这不是已删除的 `replan*` 的回归

`include/path_follower/velocity_planner.hpp` 的类注释记录了历史上 `replan*` 系列接口被删除的
理由：**把"当前速度"寄存在轨迹数组里当种子** → 曲率减速反复复合、Ruckig 边界输入下不收敛、
STOP 截断值泄漏进后续规划。

惰性规划**不是同一件事**：

- 种子仍然是固定的 `(min_linear_velocity, 0)` 边界，不是当前实速；
- 每一段仍然只规划一次，规划完之后全程只读；
- 只是把"规划的时刻"从受理挪到了段起点。

只要守住 §4.4（不碰 step model 状态），它不会把那批问题请回来。
**实现时应把这段区别写进注释**，否则下一个人看到"阶段转换时调用 planner"会本能地以为是老毛病复发。

## 6. 建议落地顺序

1. **阶段三惰性化** —— 收益最大（修的是有补丁记录在案的真 bug，3.3 s）、改动最小、
   不在起步关键路径上；§4.2 的"失败时机后移"在阶段三几乎不存在（那时位置已经到点了）。
2. **起步 s 原点 re-base** —— 见 §7 备选方案 B。双向都治，改动小，能把起步 2 s 里的 1.2 s 拿掉。
3. **阶段二惰性化 + 反向延拓** —— 结构最正确，但收益与第 2 项高度重叠，风险却是三者里最高的。
   等 1、2 落地跑一段时间再决定。

## 7. 起因与备选方案

### 起因

差速底盘，阶段一原地旋转结束后定位漂到轨迹起点**后方 2cm**：

- `velProjection`（`src/path_follower.cpp:1845`）用投影比 `K` 插值速度，
  第 1868 行 `clamp(K, 0.0, 1.0)` 在车位于起点之前时把 `ratio` 夹成 0；
- 于是 `ref_v ≡ points[0].linear_v`，而这个值是 `min_linear_velocity = 0.01`
  —— Ruckig 的**起点种子 / 底盘死区**，不是"落后 2cm 该以多快追上去"的答案；
- 0.02 m ÷ 0.01 m/s = **2.0 s**，与现场观察吻合。

反方向（定位跳到前方 2cm）则是相反的症状：查表瞬间平移，`ref_v` 从 0 跳到 `v(0.02)=0.071`
（跳 10cm 则跳到 0.208），起步窜车。

补充：2cm 远低于 `localization_jump_threshold: 0.07`，`guardLocalizationJump` 不会拦，
是直接穿透到投影里的。

### 备选方案 A：起步加速斜坡（floor）

轨迹剖面继续当"计划"，另跑一条从车当前实速起、按 `max_linear_acceleration` 爬升的开环斜坡，
两者取 max；**一旦剖面追上斜坡就永久关闭**（关闭那一帧两者相等，天然无跳变）。
放在 `velProjection` 之后、`stepTrackedLinearVelocity` 之前，障碍减速仍能压住它。

安全钳（关键）：`v_ramp <= min over j 在前方 sqrt(v_prof[j]² + 2·d_max·(s_j − s_i))`
—— 即 `applyAccelerationEnvelope` 的反向扫描改成在线求。窗口只需
`v_max²/(2·d_max)` = 0.61 m ≈ 61 点。它能**自动区分"剖面低是因为起步瞬态"（可超越）和
"剖面低是因为曲率/终点"（不可超越）**，无需为"起步就进弯"写特判。

效果：2cm 从 2.0 s → 0.28 s（斜坡加速度取 0.5）或 0.51 s（取 0.15）。
缺点：只治落后，不治超前。

### 备选方案 B：起步前 5cm 的 s 原点 re-base（推荐先做）

把速度剖面的 s 原点**强制对齐到阶段二入口时车的实际位置**，只在前 `L = 0.05 m` 内生效：

```
s_lookup = s_map + s_offset0 · (1 − s_run / L)
s_offset0 = −s_map(阶段二入口)          // 使入口处 s_lookup ≡ 0
```

- `s_map` = 车在轨迹上的投影弧长（入口处 = ∓0.02，需要在 `index==0` 时放开
  `clamp(K, 0.0, 1.0)` 的下限，才能表达负值）；
- `s_run` = 阶段二入口以来 **odom 走过的距离**（抗定位抖动，和末端 odom 锚定同源思路）；
- 线性淡出保证入口和出口两端都连续，中间单调，无交接跳变。

**关键切分：「我该多快」用 `s_run` 基准的 `s_lookup`，「我该往哪偏」（`findNearestIndex` /
前视点 / `Δx`,`Δy` / `checkTrackDeviation`）继续用 map 位姿。** 车仍然要真的走完那 2cm
走到轨迹上去，横向纠偏也必须对着真实偏差 —— 只有前馈速度查表换自变量。

> 注意与末端 odom 锚定（`src/path_follower.cpp:1727`，`end_localization_switch_distance: 0.05`）
> 的区别：末端换的是**位姿来源**（整个 pose 改用 odom 递推）；起步要换的是**查表自变量**。
> 名字对称、机制不同。**照搬末端那套（起步也换位姿源）一点用都没有** —— DR 位姿的起点
> 就是那个落后 2cm 的位置，投影照样 `K<0`，照样 0.01，照样 2 秒。

效果：

| 定位偏差 | 现状 | re-base 后 |
|---|---|---|
| 落后 2cm | `ref_v ≡ 0.01`，**2.0 s** | 跑剖面自己的起步段，**0.84 s** |
| 超前 2cm | 直接跳到 `v(0.02)=0.071`（跳 10cm → 0.208） | 从 `v(0)=0.01` 起爬，**过冲消失** |

改动量：`velProjection` 放开起点 `K` 下限 + 一个 `s_run` 累计 + 3 个成员变量 +
1 个参数 `start_reference_rebase_distance`（默认 0.05，0=关，与
`end_localization_switch_distance` 命名对仗），diff / omni 两条阶段二共用。
不碰 `VelocityPlanner`，不碰轨迹数组。

### 正交项：`max_linear_jerk` 偏低

`max_linear_jerk: 0.2` m/s³ 下，即使车精确压在起点上、走的是纯正的规划剖面，
光爬过前 2cm 也要 **0.84 s**（v 才到 0.071 m/s），加速到 0.7 m/s 要 **3.7 s / 1.28 m**。

所以要分清两件正交的事：

- **re-base 修的是"查哪个 s"** —— 治定位偏置，同时治延迟和过冲，是结构性的正确修法；
- **jerk / 加速斜坡修的是"剖面在那里有多陡"** —— 治起步本身就慢。

两者可叠加，互不干涉。建议先做 re-base（是"修正错误"），再视情况动 `max_linear_jerk`
（最简单，一个数）或上加速斜坡。
