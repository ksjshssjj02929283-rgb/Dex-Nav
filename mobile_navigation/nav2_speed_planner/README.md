# nav2_speed_planner — 离线场景验证

速度规划（五层架构第 ④ 层）的离线剖面生成器与不变量校验器。不依赖 ROS 运行时，
不需要机器人、costmap 或 bag：障碍与逐点限速由子类注入，**一次运行约 2 秒**。

它同时是两样东西：

- **回归基线** —— 24 个历史场景的 CSV 逐字节可比，改动是否影响既有行为一目了然
- **缺陷探针** —— 60 个场景 / 503 项检查，把已知缺陷钉住、让新缺陷浮出来

---

## 快速开始

```bash
# 工作区根（含 src/ 的那一层）
colcon build --packages-select nav2_speed_planner --parallel-workers 8
source install/setup.bash

# 只跑校验（CSV 输出到 /tmp/sp）
./build/nav2_speed_planner/speed_profile_gen /tmp/sp
echo $?          # 0 = 全部通过（XFAIL 不阻塞）；1 = 有 FAIL

# 校验 + 出图（总览 + 每场景四联详图）
ros2 run nav2_speed_planner gen_speed_plan_charts.py
# 缺省输出 ~/.dexe/navigation/speed_planner/
#   csv/                各场景剖面
#   speed_profiles.png  总览（距离族 / 时间域+障碍 / 交叉约束 三行）
#   detail/*.png        每场景四联详图（v-s+region / a-s+限值 / jerk / v-t）
```

出图脚本按目录 `glob` 自动发现 CSV，**新增场景不用改绘图代码**。

## 代码结构

单编译单元，四个文件各司其职：

| 文件 | 职责 |
|------|------|
| `src/tools/speed_scenarios.hpp` | 场景定义与场景表（**纯数据**，加场景只动这里） |
| `src/tools/speed_harness.hpp` | 路径构造 + 规划器注入 + 跑一个场景 |
| `src/tools/speed_checks.hpp` | 期望校验 + 不变量 + 单调性 + 跨场景检查 |
| `src/tools/speed_profile_gen.cpp` | 编排与报告 |

### 场景的两个正交维度

**`Category`** —— 这个场景在测什么（报告按类分组）：

| 类别 | 覆盖 |
|------|------|
| 距离族 | 直线 0.3 / 0.5 / 1.0 / 2.5 / 5.0 m，静止起步 |
| 运动中起步 | v0 = 0.3 / 0.6 / 1.0 |
| 弯道 | 2m 处 0.5m 弧段 r=0.5 |
| 障碍 | 起点豁免 / 中途 / 5m 路径 3m 处 |
| 终端 | 硬停（end_speed=0） |
| 交叉约束 | 障碍×弯道、障碍×终点、弯道×终点、高速×近距障碍、外部限速扫描、双障碍、短路径三约束齐 |
| 限速区 | 单区 / 双区 / 区+障碍 / 高速进区 |
| 退化输入 | 空路径 / 单点 / 2 点 / 全重合 / 含重复点 / v0 超上界 / 全路径障碍 |
| 非法输入 | NaN / Inf 位姿、零四元数、倒行路径、瞬移、负 v0、end_speed>max_speed |
| 失败策略 | 约束不可评估 × FAIL_CLOSED（必须空计划）/ × FAIL_OPEN（必须出计划） |

**`Expect`** —— 这个场景**应该**得到什么：

| 期望 | 含义 |
|------|------|
| `Success` | 非空，且全部不变量成立 |
| `EmptyPlan` | **必须**返回空轨迹（fail-closed，或输入本就无法规划） |
| `ZeroSpeed` | 非空但全程线速度为零（点数不足 / 纯原地转） |
| `Degraded` | 非空但已知违反部分不变量 —— 记 XFAIL，**必须写明 `degraded_reason`** |

> `Expect` 是必需的一维。早期版本把"非空轨迹"当成无条件断言，结果 fail-closed
> 语义（不可评估时**应该**返回空计划）在结构上无法表达，于是一个场景都没覆盖。

## 校验清单

**每场景不变量**（与剖面形状无关，因此可以安全断言）：

- 输出无 NaN / Inf
- `v ≥ 0`、`v ≤ 上界`
- `s` 与 `rel_time` 单调不减
- `|a| ≤ accel/decel 限值`
- `|jerk| ≤ max_jerk`（仅 S 型）
- 障碍带内零速（起步 0.15m 豁免窗除外）
- 末点 `v ≤ end_speed`

**跨场景性质**：

- **单调性** —— 同一条路径上移除一个可移除约束（障碍 / 外部限速）后，逐点速度不得更低。
  这是 Phase A "逐点 min 叠加"契约的端到端检验。
- **曲率不变性** —— 横向加速度限制 `v = √(a_y,max/|κ|)` 对给定半径是常数，
  不应随外部限速变化。

### 断言纪律（重要）

**只断言与剖面形状无关的性质。** 三条约束叠加后剖面该长什么样，事先写不出来；
硬写等于把当前实现当成规范钉死，反而阻碍修复。形状相关的判断留给人看详图。

**NaN 必须显式查。** NaN 的一切比较都是 false，所有 `x <= 限值` 形式的断言都会被
它静默绕过 —— 实测曾出现"全部不变量通过、实际整条计划已塌成爬行速度"的情形。

## 加一个场景

只改 `speed_scenarios.hpp` 的 `buildScenarios()`：

```cpp
{
  Scenario t;
  t.tag = "X_T_my_case";              // 前缀：X_ 交叉 / D_ 退化 / E_ 非法 / F_ 失败策略 / Z_ 限速区
  t.category = Category::Crossing;
  t.length = 5.0;
  t.v0 = 0.6;
  t.arcs = {{2.0, 0.5, 0.5}};         // 弧段：起始弧长 / 长度 / 半径
  t.obstacles = {{3.0, 5.0}};         // 障碍带：单位是路径 **x 坐标**
  t.zones = {{1.0, 2.0, 0.3}};        // 限速区：x 区间 + 限速
  t.note = "一句话说明这个场景在测什么";
  add(t);
}
```

CSV 与详图自动产出，无需改其他文件。

### 两个必须知道的坑

**① 障碍带用 x 坐标，不是弧长。** 曾试过改用弧长（想让弯道场景更好读），结果与历史
CSV 逐位对不上：路径 x 由 `x += kPointStep*std::cos(yaw)` 累加，编译器按
`-ffp-contract=fast` 会收成 FMA，与纯加法差 1 ULP，正好在 `x >= from` 边界上翻转，
使减速斜坡整体错位一个采样点。**校验侧的带判定也必须用 x**，否则弯道场景会误判
（转过 1 rad 后 x < 弧长）。

**② 直线路径用 `i*kPointStep`，弯道用累加。** 同上的浮点原因，合并成单一生成器会
破坏历史等价性。`makePath` 内保留了这个区分。

## 当前 XFAIL（13 项，均为真实缺陷）

它们**不是**"可以忽略"，只是不阻塞门禁。每一条都必须带 `degraded_reason`。

| 场景 | 现象 |
|------|------|
| `X_T_fast_near_obs` | v0=1.0、障碍在 0.5m（制动距离需 0.83m）→ 首点 `a=-16 m/s²`，限值 0.6 |
| `X_S_fast_near_obs` | 同上 S 型：jerk 限制下刹不住，以 0.935 m/s 驶入障碍带 |
| `X_T_fast_near_curve` | 同类，曲率版本，`a=-20.7` |
| `X_T/S_limit_drop_while_moving` | v0=1.0 进入 0.3 限速区 → 一个采样步内 1.00→0.30，`a=-22.75` |
| `Z_T_zone_entry_fast` | 同上的限速区形态 |
| `D_v0_over_max` | v0 超 max_speed → `a=-31.25` |
| `E_negative_v0` | v0 的符号被忽略、只用幅值：首点 -0.5 直接跳 +0.52，未建模穿越零点 |
| `E_nan_pose` / `E_inf_pose` | 单个非法位姿 → 整条计划塌成爬行速度，**无任何告警** |
| 曲率约束（跨场景） | 弯道限速随外部限速漂移 3.3 倍；同一 r=0.5 弯道横向加速度 0.031→0.347 m/s²（差 11 倍） |

**共同根因**（前 6 项）：速度包络被当作硬钳位逐点施加，从不检查初始状态在加速度
限制下能否到达包络。初始状态超出包络时，计划直接要求瞬间掉速，而非按 `decel_`
平滑收敛。触发条件包括障碍突现、区域限速变化、上游超调 —— 后两者是常规情况。

## 已知覆盖边界（读结果前必读）

**"全部通过"的含义远比字面窄。**

| 维度 | 状态 |
|------|------|
| 单次规划、常规与边界场景 | ✅ 覆盖 |
| **跨周期行为**（运动状态延续、规划原点漂移、终端可达性重判、制动锁存、跟踪欠账） | ❌ **零覆盖** —— 本工具是单次规划，这些在结构上不可见 |
| 与控制器的交互（碰撞预判、前瞻延迟补偿） | ❌ 零覆盖 |
| 真实数据分布 | ❌ 全部为合成场景 |
| 实机 / bag 回放 | ❌ 不涉及 |

还有一类断言抓不到的问题：**结果本身合法、但语义错误**。例如逐点限速被全局
`computeCruiseLimit`（取全路径非零点最小值）压平成单一速度 —— 剖面处处合法，
所有不变量都过，但功能是错的。这类只能靠看图发现。

**离线全绿 ≠ 速度规划正确。** 它只说明：单次规划在已想到的场景里不违反基本物理。
